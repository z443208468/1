# 苍岐工具用法

这里集中维护现有软件的操作方法。演出步骤与交接字段见[苍岐演出规则](../docs/苍岐演出与美术统一规则.md)，美术工序和验收标准见[苍岐美术生产规则](../docs/苍岐美术生产规则.md)。单次执行只读对应任务的操作节。

| 要执行的任务 | 本文入口 |
| --- | --- |
| 演出第 0–1 步 | 服务与章节流水线、清除本章运行数据 |
| 查资产、落库、正式稿与套装 | 查询实体与工单、登记实体与设计、登记图片需求与工单、保存演出稿与套装 |
| 上传成品、跨场复制或回填 | 图片版本、工单附件与回填 |
| 登记设计版本、按用户回执更新版本标记 | 登记实体与设计 |
| 汇集早期定版图或单场成图、回收用户决定 | [生成美术用户审核包](#生成美术用户审核包) |
| 场所白模、机位、结构图及叠图 | [场景空间白模与结构图](#场景空间白模与结构图) |
| 拆单后替换下游工单依赖 | 按实际主体替换工单依赖 |
| 返修比对 | 审核留痕 |
| 美术整图、姿势、取回与定尺寸 | Forge 生图与取回、PosePipeline、预览与定尺寸 |
| 局部修改、保底生成、差分 | ComfyUI 下的局部重绘、本地保底生成、表情与视线差分、局部改动检查与审核图、差分检查结果 |

## 路径与命令记法

根目录为 `D:/CangqiStudio/`。下文命令中的尖括号替换为实际 ID、路径或值，方括号表示可选项，省略号表示可重复的参数。下列简写先展开再执行。

| 简写 | 实际位置或构造 |
| --- | --- |
| `F/` | `D:/CangqiStudio/Cangqi-ArtLab/agent-sprite-forge/skills/` |
| `forge/<工单ID>/` 或 `<工单目录>/` | `D:/CangqiStudio/data/projects/<项目ID>/forge/<工单ID>/` |
| `P`（API 路径前缀） | `http://127.0.0.1:3002/projects/<项目ID>` |
| `assets.py <子命令> …` | `python D:/CangqiStudio/AssetWorkflow/tools/assets.py --project <项目ID> <子命令> …`。子命令的 `--help` 列出该机支持的参数。 |

PowerShell 中用 `Get-FileHash -Algorithm SHA256 <文件>` 算哈希，`Copy-Item` 复制，`New-Item` 建目录，`Set-Content -Encoding utf8` 写文本。常规 HTTP 查询可用 `Invoke-RestMethod`，multipart 上传用 `curl.exe`。正文、工单输入、贴图位置分别用 `brief-NN.json`、`input-NN.json`、`placements-NN.json`，以实际路径传入。

## 服务与章节流水线

**演出能力核对。** 在演出册指定的本机 Novel2Galgame 基线上同时查 `Novel2Galgame/packages/ir/src/schema.ts`（合法步骤及字段）和 `Novel2Galgame/packages/runtime/src/step-engine/execute-step.ts`（步骤的实际执行分支）。用该项目当前提交的真实代码核对，单有一种 IR 类型不能证明预期效果已经播放。

1. **同步和启动。** `node D:/CangqiStudio/Cangqi-ArtLab/scripts/sync-novel-context.mjs` 同步模型提示段。`Novel2Galgame/scripts/start-local.ps1` 启动本机服务时也会调用它。API 为 `127.0.0.1:3002`，工作台为 `127.0.0.1:5173`。重启时先确认实际监听者为本项目，结束对应监听进程，两个端口都释放后再启动；核对服务恢复与本项目回读。
2. **核对活动连接与指定初稿模型。** `GET /config/profiles` 读活动连接，`GET P` 读项目的 `config.defaultTextModel`，`GET /config/model-assignments` 读文本模型分配。三个 `/config/…` 地址均相对于 API 根，不带项目路径。切换连接用 `POST /config/profiles/<连接名>/activate`，之后回读。测试应带实际初稿模型名。

```powershell
Invoke-RestMethod http://127.0.0.1:3002/config/profiles
Invoke-RestMethod http://127.0.0.1:3002/projects/<项目ID>
Invoke-RestMethod http://127.0.0.1:3002/config/model-assignments
Invoke-RestMethod -Method Post http://127.0.0.1:3002/config/test-connection -ContentType application/json -Body '{"model":"<初稿模型>"}'
```

3. **固定外观。** 在本章“改编前：本章人物外观与衣装”面板依次使用“整理本章外观设定”“保存已整理的外观方案”“确认并固定本章外观”。核对 `appearance-plan.json` 的 `sourceHash`。缺 `attributed_units.json` 或 `segmentation.json` 时由本章流水线生成。
4. **运行与回读。** “运行管线/重新运行”是续跑，可按章节 done 标记跳过归属、分场，按 `mappingStatus = done`（数据库列 `mapping_status`）跳过映射，也可能复用任务缓存。查 `GET P/chapters/<章ID>/scenes`，与 `segmentation.json` 比对段 ID。每段原始产物在 `data/projects/<项目ID>/scenes/<段ID>/vn_script.json` 与同目录 `visual_prompt.json`。
5. **核对实际调用。** 查 `D:/CangqiStudio/data/logs/api.stderr.log`、`api.stdout.log` 及 `data/logs/llm-request-evidence/`。后者由 `CodexLocalAPI/server.mjs` 留存请求 ID、时间、模型、`messages`、`developerInstructions`，不含认证头。按项目、章、运行时段和请求归属核对模型及实际提示正文。

| 日志或状态 | 读取方式 |
| --- | --- |
| `Critical fidelity failures detected`、`passed=false`、`reviewStatus: failed` | 读取内容审核报告及实际文本，按演出第 1 步区分质量问题与运行问题。 |
| `LLM API error`、HTTP 4xx/5xx、`fallback triggered`、`unsuccessful result` | 追到本次请求的最终结果；内置重试后的成功与实际降级分开记录。 |
| `chapter_ready`、任务 `succeeded` | 同时核本轮请求与文件时间，状态本身不能证明使用了指定模型。 |

## 清除本章运行数据

**操作范围。** 仅对演出第 1 步判定允许清除的本章执行。先确认项目 ID、章 ID 及已有场次需求；章内已有登记需求，保留本章数据并走现有初稿分支。此处的 `app.db` 是运行数据库，PocketBase 资产库及其他章不在清理范围。

1. 停止本项目 Novel2Galgame 服务，确认 3002、5173 都不再监听。将本章目录、全部本章场景目录和本章缓存复制到 `01-初稿/运行前备份-<日期>-<序号>/`。对活动库用 sqlite3 的 `.backup "<新编号备份目录中的app.db完整路径>"` 生成一致快照，避免遗漏 WAL 中已提交的页。用 `sqlite3 -readonly "<备份库完整路径>" "PRAGMA quick_check;"` 独立打开快照，应返回 `ok`，再对照源库核本章标志和预检行数。记录各备份文件与 SHA-256。
2. 依下表清点，预览匹配项，保留实际路径与各表目标行数。源文和外观方案均须保留。

| 位置 | 仅本章需清除或重置的对象 |
| --- | --- |
| `data/projects/<项目ID>/chapters/<章ID>/` | `narrative_units.json`、`attributed_units*.json`、`segmentation*.json`、`manual_*.json`、`narrative-model-responses/`。保留 `source.txt`、`appearance-plan.json`、`appearance-draft.json`、`appearance-history/`。 |
| `data/projects/<项目ID>/scenes/` | 本章的 `<章ID>_scene_*/` 目录。 |
| `data/cache/<项目ID>/` | 文件名含本章完整 ID 并已核对实际归属的缓存。 |
| `data/config/app.db` | `chapters` 中本章行状态改 `raw`，`scene_count` 置 0，`parsing_done`、`attribution_done`、`segmentation_done`、`mapping_done`、`review_done` 置 0。仅删除 `scenes`、`tasks`、`pipeline_runs` 中 `chapter_id` 等于本章 ID 的行。 |

3. **只读预检。** 用同一个项目数据库做预检与写入。先以只读方式检查表、列、主外键和章 ID，记录目标章当前标志及三张子表的本章行数。工作台已登记需求的排除检查在停服前完成，不能用子表行数代替。通过 `.read` 执行脚本前先检查脚本内容；下列片段按阶段分别执行。

```powershell
sqlite3 -readonly D:/CangqiStudio/data/config/app.db
```

```sql
.schema chapters
.schema scenes
.schema tasks
.schema pipeline_runs
PRAGMA foreign_key_list(scenes);
PRAGMA foreign_key_list(tasks);
PRAGMA foreign_key_list(pipeline_runs);
PRAGMA foreign_key_check;
```

同时用 `.schema` 查全库表定义与触发器，核对其他表指向这四张表的反向外键（含 `ON DELETE CASCADE` 及 `ON UPDATE` 动作）。逐条确认可能联动的行仍属本章和这四张运行表。若可能越出任一边界或改动资产记录，不执行该次写入，按演出册“严禁阻断”规定的排查路径继续。

把实际章 ID 绑定为 `@chapter_id`。同一绑定和计数查询分别用于事务前、事务内及提交后核对。每次新开 sqlite3 连接须重新绑定并回显章 ID。

```sql
.parameter init
.parameter set @chapter_id "'<完整章ID>'"
SELECT @chapter_id;
SELECT 'scenes' AS table_name, COUNT(*) AS row_count
FROM scenes WHERE chapter_id = @chapter_id
UNION ALL
SELECT 'tasks', COUNT(*) FROM tasks WHERE chapter_id = @chapter_id
UNION ALL
SELECT 'pipeline_runs', COUNT(*) FROM pipeline_runs WHERE chapter_id = @chapter_id;
```

4. **准备变更。** 两个服务仍须停止。将目标运行文件按上表和备份清单移出活动路径并保留可还原副本。SQLite 与文件系统不能一起回滚。只在确认能还原本次移动的所有文件后进入写事务。

5. **一次短事务。** 以普通读写模式重新用 `sqlite3` 打开同一 `app.db`。本机实库中 `chapters` 的章标识列是 `chapter_id`（主键），状态列是 `status`；`scenes`、`tasks`、`pipeline_runs` 都有 `chapter_id` 列，`scenes.chapter_id` 对 `chapters` 为 ON DELETE CASCADE，`pipeline_runs.chapter_id` 对 `chapters` 无级联。预检发现表结构或外键与此不同时，以预检结果为准，必要时调整三个 DELETE 的顺序（依赖行先于被引用行），并重做预检。

在该连接重新绑定并核对 `@chapter_id`；开启外键检查后再开事务。先执行以下语句，确认章 ID 未变且只命中一条目标章行；否则立即回滚。

```sql
PRAGMA foreign_keys = ON;
BEGIN IMMEDIATE;
SELECT COUNT(*) AS target_chapters
FROM chapters WHERE chapter_id = @chapter_id;
```

在**同一连接、同一事务**中再执行下段。每条修改后记录影响行数。章更新必须恰为一行，对应三表的删除行数须与预检一致。任何 SQL 错误，停止执行后续写语句并回滚。

```sql
UPDATE chapters
SET status = 'raw', scene_count = 0,
    parsing_done = 0, attribution_done = 0, segmentation_done = 0,
    mapping_done = 0, review_done = 0
WHERE chapter_id = @chapter_id;
SELECT changes() AS chapters_updated;

DELETE FROM tasks WHERE chapter_id = @chapter_id;
SELECT changes() AS tasks_deleted;
DELETE FROM pipeline_runs WHERE chapter_id = @chapter_id;
SELECT changes() AS pipeline_runs_deleted;
DELETE FROM scenes WHERE chapter_id = @chapter_id;
SELECT changes() AS scenes_deleted;
```

6. **提交前回读。** 保持同一连接，重跑目标章计数与三表计数，再查本章状态及外键。目标章一行、状态为 `raw`、列出的六个数值全为 0，三张子表本章剩余行数均为 0，外键检查相对预检无新增问题，才可提交。

```sql
SELECT status, scene_count, parsing_done, attribution_done,
       segmentation_done, mapping_done, review_done
FROM chapters WHERE chapter_id = @chapter_id;
PRAGMA foreign_key_check;
```

| 结果 | 当前连接及文件处理 |
| --- | --- |
| 全部核对通过 | 单独执行 `COMMIT;`。提交后重新回读目标章状态及各表本章行数。 |
| 任一条件不符、出现错误或提交未成功 | 事务仍活动时单独执行 `ROLLBACK;`。还原本次移出的文件，对照备份清单核实路径和哈希。重跑前重新预检。 |
| 连接意外中断或提交结果不明 | 保持停服。重新打开数据库，只读核对章状态与各表行数，查明事务实际结果后按相应分支处理。必要时以停服时的备份还原数据库及本次移动的文件，并重新核对。 |

把实际删除路径、各表改动行数和回读结论写入 `00-范围.md`。只有确认本章已完整清除且保留项无误才启动服务，从头运行。

| 操作 | 子命令／读取结果 |
| --- | --- |
| 查询实体和引用它的工单 | `search --query <名称> [--kind <类别>]`。按实体名称还能找到引用它的工单，搜索不会自动合并实体。 |
| 查询实时工作台资源 | `registry-search --query <关键词> [--kind <类别>]` 或 `GET P/registry`。可看资源状态、具体版本的图像地址、`production.purpose` 与人物 `portraitRole`。 |

| 读步骤绑定 | `scene-context` 的 `step_bindings` 对应工单的 `step_ids`、成图、工作台资源和各实体版本。这个映射在资产管理中保存，演出稿格式不变。 |
| 接着做下一单 | `next` 列未完成工单，排除状态“已撤销制作”的工单。已完成及撤销记录仍可查询。 |
| 回读某张工单 | `job-get --id <工单ID>` 从数据库恢复工单文件。`task.json` 存当前状态及实体引用，`brief.md` 是工单正文。 |

## 登记实体与设计

- 首次登记实体可用 `assets.py register --name "<实体名>" --kind <类别> --description "<说明>" --evidence "<原文位置>" --first-scene <段ID>`。实际记录还须按规则填所属关系、`parent_entity_id` 和依据。已有实体的状态用 `assets.py update` 补写，查询见上一节。
- 新增设计用 `assets.py design-add --entity <实体ID> --input <JSON文件>`。工作台“新增设计版本”不写 `design_path`。实际参考路径数组 `references` 中的文件会复制进实体版本目录，旧版保留。JSON 输入示例：

```json
{
  "description": "待用户审\n<设计说明>",
  "design_path": "D:/CangqiStudio/data/projects/<项目ID>/forge/<工单ID>/gen-NN/generated.png",
  "state": "可复用",
  "references": ["<参考文件实际路径>"]
}
```

- 过美术册共同四技术底线和生产者一瞥后登记。用 `assets.py job-update --id <设计工单ID> --input <JSON文件>` 写 `{"state":"可复用"}`，再用 `job-get`、`job-context` 核目标实体、版本号、图路径、文件指纹和下游绑定。“可复用”是业务状态。用户审图记在该具体版本和审核包的回执中，角色早期检查点依美术册 A5 调度。
- 新设计版本首次登记把“待用户审”写在 `description` 首行，宿主生图或本地保底等说明留在后续行。登记后从当前版本的 `notes` 首行读有效标记。没有现行标记才读 `description` 首行；历史“已通过设计图审”等 AI 记录保留原文，用户审图状态仍按待审办理。“用户已审”须有同一对象、版本和指纹对应的真实用户通过回执。仅有界面的“可复用”或资源的“已采纳”不能签为用户通过。
- 用户明确通过或接受指定的较轻版后，按实际回执更新该版本的 `notes`。先用 `job-context` 读回原备注与图像版本，再将修改后的完整备注写成 UTF-8 的 `design-notes.json`。若原首行已有现行标记，仅替换该标记；保留原有正文、历史标注与特殊来源。写入后再读相同实体及版本，核图、指纹和标记。用户退回则把原版退出可领取范围，原图、原备注历史和退回理由留档，另开修订单。新版本从“待用户审”开始。

```json
{"notes":"用户已审\n回执 <回执ID>，<用户答复证据位置>，SHA-256 <实图指纹>\n<其余已有备注原样保留>"}
```

```powershell
curl.exe -sS -X PATCH -H "Content-Type: application/json" --data-binary '@design-notes.json' http://127.0.0.1:3002/projects/<项目ID>/registry/workflow/design/<实体ID>:v<版本号>
```

## 登记图片需求与工单

**图片需求。** 在工作台“资产管理 → 登记<类别>”勾选“作为某演出段的制作需求”，选本章演出段。名称填 `<场名> / <需求ref>`，因为接口会改写请求内的 `ref`。人物填表情、姿势、视角、衣装四维。界面没有用途输入框，可通过下列接口写入，完成后再上传或采纳复用图。

| 方法与项目内路径 | 请求结构与读取要点 |
| --- | --- |
| `POST P/registry/demands` | `{chapterId,sceneId,resource:{ref,kind,label,description,purpose,portraitRole,reason,entry,exit,unitIds,characterId,expression,pose,view,outfit}}`。人物填 `characterId` 与四维已有资源 ID。背景／CG 填 `label`。 |
| `PATCH P/registry/<资源ID>/demand` | `{description,reason,brief:{purpose,portraitRole,unitIds,reason,entry,exit}}`。`brief` 整体替换，应带回旧记录中其他字段。带用途的登记会把说明、用途、进入退出、原文等展开成行，CG 可能另有前后与本帧。 |

**工单。** 工作台“制作工单”页签新建，填标题 `<场名>审定 / <工单ref>`、段、类型、初态；或用 `assets.py job-create --scene <段ID> --input <JSON文件>`。示例为依赖成图原段上的设计修订工单。

```json
{"type":"design","state":"待设计","title":"<场名>审定 / <实体名>设计修订","entities":[{"entity_id":"<实体ID>","design_version":null}],"depends_on":[]}
```


| --- | --- |

**按场汇集。** 主会话将本次实际记录的路径列在 `items`；文件多时从现有调度结果归集，不让用户逐行抄录。例中 `scope-ids.json` 是从本场授权与 5f／人物状态实际映射取出的 ID 数组（有工单取工单 ID，无本场单取状态／资源 ID）。`scope-evidence.md` 保存该范围的原始回读。文件名示例为本地约定，不要求工作台提供新接口。

```powershell

$index = [ordered]@{
  project = '<真实项目ID>'; scene = '<真实章ID>'; phase = 'scene'
  scope = @(Get-Content './scope-ids.json' -Raw -Encoding utf8 | ConvertFrom-Json)
  scope_evidence = 'scope-evidence.md'; scope_complete = $false; items = $records
}
if (Test-Path './receipts.json') { $index.receipts = 'receipts.json' }

```

本场全部美术项由完整 5f、实际演出引用和跨场复用核齐后，主会话才把 `scope_complete` 置为 `true`。暂未授权或仍等前置也须在范围内逐项记 `waiting`。仅完成一个批次继续用 `false`。角色定版的该值是针对这个角色本轮适用的完整范围。

早期定版将 `phase` 改为 `checkpoint`，每包一个角色。加 `"checkpoint":{"character":"<角色ID>","cg_only":false,"evidence":"<已审可见性／4c及该角色适用定版范围文件>"}`，各项的 `character` 填同一角色。通常汇集身份、所用衣装和首张基准样板。已审材料明确仅在 CG 出现时设 `cg_only:true`，只收身份与所用衣装；不为定版虚建样板。整场填写 `scene`。清单漏项、无图、技术失败、空间材料或人物基准缺失，会生成标记缺口的进度包，只汇报进度，不发正式逐项回执。是否可以收口仍按美术册 A7 核对全部实际授权及待办。包可重建，原审核轮目录及用户回复不覆盖。

**记录用户答复与返工。** 回复按 `回复清单.txt` 编号记“通过／退回／接受较轻版＋一句说明＋条款”。主会话将明确选择的对象、实际版本和 SHA-256 与该轮包匹配，保留原始用户答复的本地证据。若指定较轻版，先定位用户点名的旧版、回读其指纹及实际采纳结果，再记录那一版。回执中每个对象使用一个唯一 ID，按答复时间先后存入 `receipts.json`；同一答复涉及多个对象时逐项映射，一次退回只记一次。缺少明确对象或版本时保留待确认。以下为一条记录的结构：

```json
[{"id":"<回执ID>","actor":"user","project":"<项目ID>","scene":"<当轮章ID>","phase":"scene","key":"<状态／实体／资源ID>","version":"<用户实际选择的版本>","sha256":"<该版本指纹>","decision":"退回","quote":"<用户原话>","evidence":"<原始回复UTF-8文本>","clause":"<对应条款>","rework_job":"<已登记的返工单ID>"}]
```

定版回执另写 `character` 和 `kind`，基准须为该角色首张确认样板。 普通场审通过只证明该图可用于当场。若同一份历史场审原话还明确把该版选为该角色定版，可在原回执注明 `confirms_checkpoint:true`、实际角色及类型并保留原话，避免再问。后来的同版退回仍有效。后续整场引用该样板时写 `checkpoint_base:true` 并保留原回执。

本轮通过项依本节与“登记实体与设计”回写、回读；退回项用原工单、原版本、原回执查是否已有返工单，有则续办。没有则按上文设计／成图工单的既有登记方法建立返工单，注明原版本、原因、具体条款和受影响下游，回读真实 ID 后填 `rework_job`。尚未取得 ID 时省略该字段。返工产物过技术底线、登记新版本，带旧版及新证据再交用户。程序从实际回执整理 `返工待办.json` 和版本索引；文件生成不代表业务系统已建单。用同一输入及新增真实回执输出到下一轮包，保留两次审查轨迹。没有逐项依据的“通过”、旧 AI 审图标记及程序生成的报告都不作为用户回执。


先用同一包装器运行所用 CLI 的无写入检查及 D 盘目录回读，并确认该 D 盘 Codex 运行目录有本次准用的连接。已有浏览器、ComfyUI 或宿主进程不会因包装器改变设置；其存储须分别在本机核对。若运行记录显示仍写 C 盘，记录实际路径，再修正该进程的配置。试点 stage4 的首次调用无法排除 C 盘写入，重试只确认了该次 CLI 数据库、临时和输出位置。不要仅凭最终 PNG 在 D 盘推断全部缓存位置。

**S1–S3 数据。** 从空白 `scene.template.json` 起填一份场所的 `scene.json`。设计清单记录每个组成的登记版本、设计图与原文依据，并说明平面与剖面采用的尺度。模板没有可直接生产的实体或尺寸。坐标数组均为米制 `[东, 上, 北]`；同一场所各状态共用坐标原点，存在场所中但不入本机位的物体仍入清单。每个实体在 `entities` 只列一次，填真实 `entity_id/design_version/design_path/source`；类别、主体名称不能代替实体 ID。场所自身也列入，可在只有组成部分有几何时留空 `parts`。实体同版本的多块几何在其 `parts` 填有区别的局部编号和材质分区；清单记录各部分的数量、相对方向及所据设计。版本、实际 ID、原文与尺寸出处由非人物线按 S1 查回原件。

| 数据 | 填法 |
| --- | --- |
| 几何 | 每块有 `id, kind, material, center`，可有 `yaw_deg`（正角从东转向北）。`box` 用三维 `size`；`cylinder` 用 `radius_top/radius_bottom/height`；`tube` 用按顺序的局部 `points` 和 `radius`；`mesh` 用局部 `vertices` 和每组三个从 0 起的顶点索引 `faces`。后两者的局部坐标在旋转后加上 `center`。复杂开口由墙片、门框和实有门扇等几何围出，避免用整块盒子把门洞封死。 |
| 状态与材质 | `states[].id/source` 取当前工单状态及依据。每个材质名在 `materials` 映射为 `{"surface":"所绑定版本的材质依据","clay":"#a0a0a0","roughness":0.9,"metalness":0}`，明度体现分区，粗糙度和金属度取 0–1。`light` 填天空色、地面反射色、半球光强、定向光强及颜色、指向光源的向量、是否投影。按工单设置；阴天无方向性投影可设 `sun:0, shadows:false`。仅有已定演出或设计依据的状态差异才用 `part.states` 指定适用状态（省略等于所有状态）。固定组成不得借该字段从某个机位消失。 |
| 相机 | 每机位填写 `id/source/pos/target/vfov/near/far/resolution`；`pos[1]` 为眼高，`vfov` 为垂直视场角（度），`near/far` 为米。`resolution:[宽,高]` 应对应工单画幅，近远裁切需覆盖实际场所。相机位置、焦向、视场角或画幅改变即重出该机位参考。 |
| 俯视 | `top.png` 采用同一场所数据，正北朝上，叠加本机位视锥。在 `part.plan:false` 标明需从俯视图略去的覆盖构件（例如屋顶）；此标志只影响俯视图，不参与镜头裁切。视锥远于场所的部分可能超出平面图，实际参数保存在回执。 |

**S4 渲染结果。** 输出精确输入副本 `scene-snapshot.json` 和 `visibility.json`，含源文件 SHA-256、版本、相机、状态、实体 ID／设计版本／来源、每个实体的分色 RGB，并在 `pass_sha256` 记录六张图的指纹。另有 `clay.png`（该工单光照）、`depth.png`（近白远黑，按机位 near/far 线性映射）、`normal.png`（相机空间）、`line.png`（可见几何硬边）、`semantic.png`（无抗锯齿的精确实体分色，黑为背景）、`top.png`。

`visible_px` 来自完整场景的深度测试。`unoccluded_projection_px` 是相同机位仅画该实体时的覆盖面积。两者之差包含其他实体遮挡，`occluded_by` 给出实际可见的前景实体及遮挡像素数。`visible_bounds_xyxy` 为画面左上原点的可见包围框（含两端）。依据像素和原设计双向核查应入画实体；视锥内包围盒相交但未落像素记 `no_raster_sample`，可能是过细、边界或空隙，需复查尺寸、视线或按相同比例提高分辨率。`no_active_geometry` 表示该状态没有几何，不能据此认定物体被遮住。按实体分色，属于同一已登记实体的各零部件共用颜色，细节数量另对线稿和设计图核。

**S5 结构图。** 试点记录使用已安装的 ComfyUI Qwen-Image-Edit 2509，图 1 是本机位灰模，图 2 是符合 A1 的已登记场所／主体设计图。输入白模只约束构图、数量和投影位置，设计图供辨认主体和材质；阴天光照须先体现在灰模里。记录确认这一步保住布局，同时把几何树枝和错误硬影带进了结构图。没有随包的可执行 Qwen 工作流 JSON、权重文件名、节点号、采样参数或随机种子。本机先查既有 ComfyUI 已成功的 stage1 历史或保存图谱，确认确为 2509、图1/图2输入顺序及实际加载的模型，导出 API 格式副本，保存在本单新轮次，记录来源和哈希；工作流未找回时在界面按实际 2509 安装搭建双图编辑，或从 [ComfyUI 官方 2509 工作流](https://github.com/Comfy-Org/workflow_templates/blob/main/templates/image_qwen_image_edit_2509.json) 导入。核对双图端口、实际模型与本机依赖后导出 API 版本，将其标为“现场重建”。按本手册 ComfyUI 节用现有 `comfy-run.py` 上传两张文件，`--set` 只用该副本实际的 LoadImage 节点编号，输出到本单 `stage1-NN`；回读两张输入、结构输出的哈希及本次实际参数。先用下方单图比较命令生成结构图叠图，核对相机和输入版本一致，再进 Forge。视觉偏差留 S7 交用户判断。未安装或未拿到已验证图谱时不能记本机 S5 已完成。

**S6 Forge。** 用现有“Forge 生图与取回”命令，不改路由。把 S5 生成且可回读的结构图作为第一张参考，其余参考按美术册 A4 的 S6 顺序。提示词分写布局与机位、各绑定实体版本的材质／画风、原文时段／天气、允许变化与禁止新增。交接单写明实际附图顺序、用途和版本。中断带运行 ID 时取回原作业。试点显示仅附结构图会保留模型质感，仅用线稿则容易从设计图搬入其他机位的门、台阶及远景。

**S7 叠图与跨状态。** 每个 `--pair` 依次传入该状态的 S4 输出目录与待核图。一次可检查结构图或成图，两次以上另生成分行对照。输出为逐图全分辨率轮廓叠图、`comparison.png`（每行左原图、右实体轮廓）、`inputs.json`（每项的 `input_sha256`、`visibility_sha256`、`overlay_file/overlay_sha256` 和 `comparison_file/comparison_sha256` 对应实际文件）。语义图与原渲染指纹不符时，先用该版场景数据重渲。示例沿用上述子进程包装器。

```powershell
& $py "$blockoutTools/d_child.py" $runRoot $blockoutTools $py 'compare.py' --pair '<时段甲的blockout-NN>' '<时段甲的成图.png>' --pair '<时段乙的blockout-NN>' '<时段乙的成图.png>' --out '<工单目录>/check-NN/space'
```

比较要求同一场所、同一白模输入哈希、同一相机参数，图像允许等比改变分辨率。比例不符时使用已核工单取景的导出或定尺寸映射，不能为使轮廓吻合自动裁图或拉伸。粉线是白模分色边界；开启原图与叠图对照门框、主体位置、数量、遮挡等项目，在原图上实测对应点或边界，以像素或占画宽比例记偏移并按美术册判定。图像本身没有登记实体标签，工具不自动识别漏画、加景或合格。不同状态允许的积雪、天气及材质变化应能追到各自工单，固定建筑与物件按同机位逐项比对。
